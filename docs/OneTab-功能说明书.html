1产品概述#

1.1 一句话定位

OneTab 是一个零门槛的「标签页收纳器」：点一下图标，把当前窗口所有标签页折叠成一张列表页并关闭它们，从而释放内存；需要时再个别或整体还原。

1.2 价值主张

  • 省内存：官方宣称最多节省 95% 内存（示例 1981 MB → 99 MB）。原理是减少「活动标签页数量」，而非某种黑科技。
  • 降杂乱：把标签栏从「一墙 favicon」变成可检索、可组织的列表。
  • 零成本 / 零注册：免费、无需账号、默认纯本地存储。
  • 抗丢失：关闭 OneTab 页、重启浏览器/电脑、浏览器崩溃都不丢列表（数据落在扩展存储，不在页面里）。

1.3 目标用户

重度多标签用户：研究者、开发者、内容消费者、多任务办公者。「先收起来，之后再处理」是核心心智模型。

1.4 平台与商业模式

维度内容
平台Chrome、Firefox、Edge、Safari 及更多 Chromium 浏览器
内核要求Chrome 115+（2023-07）为下限；依赖 tab groups 与 MV3（Safari 上不支持文件夹/搜索/云同步等新功能）

4详细功能说明#

4.1 收集 / 收起（Collect）#

主操作：点击工具栏图标 → 收起当前窗口全部标签。用户点一下 OneTab 图标，扩展读取当前窗口所有标签的元数据，批量关闭它们，并把它们写成一个新标签组，同时打开 OneTab 列表页展示结果。

触发入口（共 4 类）

  • 工具栏图标：默认直接执行「收起当前窗口」；若在选项中启用了弹窗，则图标改为打开弹窗（弹窗内含快捷列表与操作）。
  • 页面右键菜单：在网页内右键可展开 OneTab 菜单，支持「发送当前标签 / 所有标签 / 其他标签 / 左侧标签 / 右侧标签到 OneTab」等粒度。
  • 标签栏多选：先在浏览器标签栏按住 Ctrl/⌘/Shift 多选，再用右键菜单只把选中的标签发送到 OneTab。
  • 键盘快捷键：默认 Alt+Shift+1（Windows/Linux）、Option+Shift+1（Mac）打开 OneTab；另有「模拟点击图标」的快捷键可配置，用于把当前窗口全部标签送入。

策略选项（需在选项页配置）

  • 固定标签：是否连同 pinned 标签一起收起（默认通常保留固定标签）。
  • 重复标签：是否允许/自动去重。
  • 无痕模式：需在浏览器层面单独授权扩展在无痕/隐私窗口运行。
实现要点（省内存的真实机制） 真正省内存靠的是「关闭标签页」——标签页一旦关闭，其渲染进程即被系统回收。不要把 chrome.tabs.discard()（只是挂起渲染进程、标签仍在栏上）与 OneTab 的做法混为一谈；网上部分「深度解析」文章把 OneTab 描述为使用 discard()，与官方「转换为列表、标签不再打开」的描述不符，待解包验证。

恢复语义

收起后原标签被关闭；恢复时通过 chrome.tabs.create() 重新打开 URL。不保证恢复页面状态（滚动位置、表单内容、已登录会话内的临时状态），这是所有同类扩展共同受浏览器安全模型限制的边界。

4.2 查看与恢复（View & Restore）#

  • OneTab 页面：一个全页面列表，按组展示已保存标签；每组显示标签数量、标题、URL、favicon。
  • 单条恢复：点击某条标签即在新标签页打开它。
  • 整组恢复：点击组的「恢复」按钮，一次性打开该组全部标签。
  • 全部恢复：恢复所有组。
  • 恢复后行为：可配置「恢复后是否从列表移除」「恢复到当前窗口还是新窗口」。
  • 锁定组的特殊语义：从锁定组还原的标签仍保留在 OneTab 列表中（相当于「复制打开」而非「移动打开」）。

4.3 组织与整理（Organize）#

  • 拖拽排序：拖动标签条目改变组内顺序。
  • 拖到空白新建组：把条目拖到列表空白区域即创建一个新组。
  • 拖组入组合并：把一个组拖到另一个组上，两组合并。
  • 文件夹（v2）：把组归档到文件夹中，形成「文件夹 → 组 → 标签」的层级组织。
  • 重命名：点击「More」→「Name the tab group」为组命名；v2 亦支持双击重命名。
  • 星标置顶：点击「More… → Start this tab group」加星，星标组固定置顶，多个星标组按加星顺序排列。
  • 锁定：点击「Lock this tab group」加锁图标，防止误删。
  • 多选：点击条目上的勾选图标多选，右键勾选图标可看到批量操作（批量删除、批量恢复、移动到组等）。
  • 删除 / 清空：删除单条、删组、清空列表（可在选项里配置「恢复后清空列表」）。

4.4 搜索（Search）#

  • 页面内搜索栏（v2）：在 OneTab 页顶部输入关键词即时过滤已保存标签；按 / 可快速聚焦搜索框。
  • 地址栏搜索：即使不在 OneTab 页，也可在浏览器地址栏输入 11 + 空格 + 关键词，直接在地址栏检索 OneTab 列表（基于 omnibox 关键词）。
  • 搜索维度：标题、URL（待确认是否含备注/文件夹名）。

4.5 任务 / 星标 / 备注（v2）#

  • 星标：标记重要条目/组。
  • 任务：给条目加待办标记，再点一次标记为完成，用于「这批标签还没处理完」的场景。
  • 备注：为内容添加文字说明，帮助日后回忆「为什么当初留着这些标签」。

4.6 快捷列表 Quick List（v2）#

OneTab 页上有一个独立的「快捷列表」列。把重要条目拖入该列即可随时访问；若启用了弹窗，点击工具栏图标即可查看快捷列表内容。这是对「高频使用项」的一层轻量置顶。

4.7 导出 / 导入 / 分享#

  • 导出：把标签列表导出为 URL 文本清单，可保存/迁移。
  • 导入：把 URL 清单（或分享页内容）导入回来，用于跨电脑迁移。
  • 分享为网页：把某个组上传到 www.one-tab.com 生成公开网页链接，并生成二维码，方便跨设备/跨人获取。这是唯一会把数据上传到服务端的功能。
  • 复制链接：从组的下拉菜单复制链接到剪贴板。
  • 无扩展时的恢复：官方提供 datadump-1.1.zip（一个临时解包扩展），在无法升级的旧浏览器中读取并导出旧数据，再在新环境导入。

4.8 同步与备份#

4.8.1 OneTab 的做法（参考，v2 付费）

  • 端到端加密：宣称使用 AES-256 高强度加密，密钥只在用户手中，开发者不可见备份内容。
  • 跨浏览器同步：在 Chrome / Firefox / Edge 之间同步；一处改动，其他设备即时可见。
  • 免费 vs 付费：免费扩展仍是纯本地存储；云备份/同步为付费订阅（官网无公开定价页）。
待验证同步是 v2 的新能力，官方站点措辞为「Coming soon / 即将推出」与「已推出」并存；第三方评测普遍标注其为「未经证实 / 无公开定价」。

4.8.2 my-tab 方案：基于 OneDrive 的文件级同步与备份（设计决策）

决策不自建云端、不做 E2E 加密、不接 Microsoft Graph API。把 OneDrive 当作纯粹的「文件搬运工」：扩展只负责把整库导出一个 JSON 快照文件、以及从该文件读取恢复，跨设备同步完全交给 OneDrive 客户端完成。简单、可审计、零服务端成本、无需账号对接。

职责边界：my-tab 只做「读写一个本地 JSON 文件」；OneDrive 负责「把这个文件同步到云端和其他设备」。两者通过文件系统解耦。

数据契约（快照文件）
{
  "format": "my-tab-backup",     // 固定标识，用于校验
  "schemaVersion": 1,            // 与 Store.version 对应，供迁移
  "deviceId": "<uuid>",           // 标记来源设备，便于冲突判断
  "exportedAt": 1730000000000,   // 导出时间戳（毫秒）
  "store": { /* 第 7.3 节的 Store：folders / groups / quickList / settings */ }
}

文件名建议固定为 my-tab-backup.json；如需历史快照，另存 my-tab-backup.<ISO时间戳>.json 并保留最近 N 份。

两条落地路径
路径做法体验兼容性
A · 目录句柄（推荐） 用户在选项中点「选择 OneDrive 备份文件夹」→ File System Access API 的 showDirectoryPicker() 取得目录句柄 → 句柄存 IndexedDB → 之后可静默读写该目录下的快照文件 一次授权，长期自动备份 Chrome / Edge 支持；Firefox、Safari 不支持
B · 下载目录兜底 用 chrome.downloads 把快照写到默认下载目录（如 my-tab/backup.json）；恢复时用 <input type=file> 选回文件。用户把 OneDrive 指向该目录或其子目录 需手动点导出/导入，无自动 全平台可用

策略：优先用 A，检测到 API 不可用时自动降级到 B。

触发时机与冲突处理
  • 触发：① 每次收起/组织后（防抖）自动备份；② 浏览器启动时自动读取合并；③ 选项页提供「立即备份 / 立即恢复」按钮。
  • 合并策略：按 id（uuid）做并集，同 id 以 updatedAt 较新者为准（last-write-wins）；删除用软删除标记（deletedAt）传递，避免「A 删除、B 合并后又复活」。
  • 冲突：写入前先读取当前文件内容并合并，再落盘，减少覆盖丢失；时间戳快照可作手工回滚点。
  • 防呆：写文件采用「先写临时文件再替换」，避免 OneDrive 正在上行时读到半截文件。
明确不做的（保持简单）
  • ❌ Microsoft Graph API / OAuth 登录（需 Azure 应用注册、client id/secret，复杂度高，收益低）。
  • ❌ 端到端加密（快照为明文 JSON；后续如需，可作为可选项加口令加密，不默认开启）。
  • ❌ 实时推送同步（改为「变更触发 + 启动拉取 + 手动」三种时机）。
  • ❌ 自建服务端。
后续可选升级若日后确需实时/免配置同步，再评估 Graph API 或托管后端；当前不做，避免过度设计。

4.9 设置项（Options）#

选项页（options.html，在独立标签页打开，见真实 manifest）至少包含以下可配置项：

  • 启动行为：是否在浏览器启动时打开 OneTab 页。
  • 固定标签：是否把 pinned 标签一并收起。
  • 重复标签：是否允许重复 / 自动去重。
  • 恢复行为：恢复到当前窗口还是新窗口；恢复后是否从列表移除；是否清空列表。
  • 弹窗：是否启用工具栏图标弹窗（影响图标点击行为）。
  • 快捷键：查看/跳转到快捷键设置入口。
  • 安全/隐私相关项：如是否允许无痕窗口（需浏览器层面配合）。
  • v2 新增：语言、主题（深色模式）、保存模式、备份选项、回收站与重复链接管理、安全设置等（具体条目待解包确认）。
  • my-tab 备份相关设置（见 4.8.2）：备份目录（OneDrive 文件夹）、自动备份开关与频率、启动时自动合并、保留快照份数、「立即备份 / 立即恢复」入口。

4.10 界面与主题#

  • 深色模式：官方明确提供深色主题。
  • v2 重设计：界面较 v1 更「应用化」，但也因此被大量老用户吐槽（见第 10 章）。my-tab 应保留极简气质。
  • 多语言：48 种（v2.18）；v1 早期为 30 种。

5交互与用户流程#

5.1 核心流程：收起（Save / Collapse）

用户点击图标 / 快捷键 / 右键菜单
      │
      ▼
查询当前窗口标签  chrome.tabs.query({currentWindow:true})
      │
      ▼
按策略过滤（排除固定标签? /去重? /排除 OneTab 自身页? / 按多选子集）
      │
      ▼
记录元数据 { url, title, favIconUrl, pinned, lastAccessed, windowId, index }
      │
      ▼
写入存储 chrome.storage.local  ← 先落库，后关标签（防丢关键点）
      │
      ▼
批量关闭标签  chrome.tabs.remove([...tabIds])
      │
      ▼
打开 / 聚焦 OneTab 列表页，展示新组
顺序很重要「先持久化、再关闭」是防数据丢失的核心。若反过来（先关再写），在写入前崩溃即会丢失全部标签。

5.2 核心流程：恢复（Restore）

用户点击条目 / 组的「恢复」
      │
      ├─ 单条：chrome.tabs.create({url, active:false})
      ├─ 整组：对组内每条依次 create（可控制是否新窗口）
      └─ 全部：遍历所有组
      │
      ▼
按设置决定是否从列表中移除（锁定组不移除）
      │
      ▼
写回存储并刷新 UI（用事件广播通知其它页面）

5.3 关键竞态与边界

  • 并发收起：多窗口同时触发时需串行化写入，避免丢更新（建议用「读-改-写」+ 简单锁，或集中由 service worker 串行处理）。
  • MV3 service worker 生命周期：后台可能随时休眠，所有持久状态必须落 chrome.storage，不能只放内存变量。
  • 页面对存储变化的响应：多标签同时打开 OneTab 页时，需通过 chrome.storage.onChanged 或 runtime.sendMessage 同步 UI。
  • 关闭最后一个标签：若窗口仅剩 OneTab 页并再次收起，需避免把自己也收进去（应排除扩展自身页面）。
  • 恢复顺序：整组恢复时保持原 index 顺序，避免打乱用户预期。

7数据模型（逆向重点）#

本章为推断模型受限于未能解包二进制，以下实体/字段为基于官方行为与 MV3 惯例的合理建模，用于指导实现；真实键名与结构需按第 11 章方法解包后校正。

7.1 存储位置已证实

  • 官方故障排查原文：「OneTab data is stored in your browser's internal database」→ 对应扩展的持久化存储（chrome.storage.local，底层为浏览器 profile 目录下的 LevelDB）。
  • manifest 同时申请 storage + unlimitedStorage，说明数据量可达很大且需突破默认配额。
  • v2 提示「使用了与 v1 不同的浏览器数据库」，说明 v2 更换了存储后端（v1 可能为 localStorage，v2 为 chrome.storage.local/IndexedDB，待验证）。
  • 数据随浏览器 profile 走：卸载扩展 / 重置 profile 会删除数据（官方反复警告）。

7.2 实体关系（推断）

7.4 序列化 / 压缩 / 加密待验证

  • 本地存储：很可能直接以 JSON 结构存入 chrome.storage.local（必要时按组切分键值以规避单值体积）。
  • 云同步：宣称 AES-256 端到端加密，密钥派生自用户口令；同步后端域名证据为 https://www.one-tab.com/*（见权限沿革 2025-09-24）。
  • 部分第三方克隆实现使用 LZ-string 压缩 + AES-GCM 加密（可作为参考技术选型）。
  • my-tab 决策（见 4.8.2）：不做端到端加密。本地与 OneDrive 快照文件均为明文 JSON；如快照体积较大，可选用 LZ-string 压缩（仅降体积，不涉安全）。数据保密性由 OneDrive 账号自身的安全机制承担。

9.1 权限逐项解读（v2.x 当前）

第三方安全评估：「中等风险影响 / 极低风险可能性」——即权限较敏感（能读标签），但发布者信誉良好。

9.2 隐私承诺（官方原文要点）

  • 标签 URL 绝不传输给 OneTab 开发者或任何第三方。
  • 域名图标由 Google 生成（t2.gstatic.com）。
  • 唯一例外：用户主动点击「分享为网页」时，把该组上传为网页。
  • 商店隐私声明：开发者「不会收集或使用你的数据」，不出售给第三方。
对 my-tab 的启示「本地优先 + 唯一明确出口」是 OneTab 获得信任的关键叙事。my-tab 应默认纯本地，任何外传都必须显式、可审计。

10边界与已知问题#

10.1 数据丢失场景（官方故障排查页列举）

原因说明
卸载 / 重装扩展浏览器会删除扩展数据；官方反复警告不要用重装来「修复」问题
第三方清理软件BleachBit、Advanced SystemCare 等会破坏/删除浏览器内部数据库
Firefox「刷新」误点会把 Firefox 重置为默认，删除 OneTab 数据
磁盘空间不足写入失败会导致数据库损坏或被删
崩溃 / 硬件故障写入过程中崩溃可能造成损坏
浏览器 profile 切换 / 重置不同 profile 相互独立，数据不共享

官方给用户的建议：定期导出，或使用云备份/同步。用户评价中「更新导致数据消失」是最常见的差评点之一 —— my-tab 必须把「迁移/升级不丢数据」当作一等公民。

10.2 兼容性与性能

  • 需 Chrome 115+；老版本 Chromebook 不再兼容。
  • Safari 上不支持文件夹/搜索/云同步等新功能（浏览器限制）。
  • 第三方 Safari 扩展可能干扰加载。
  • 重站点/非 Chromium 浏览器存在性能问题（后台主线程阻塞），标签数千条时会变慢。

10.3 功能缺口（用户呼声）

  • 缺少「整组保存/恢复」与「保留文件夹层级状态」。
  • v2 的 UI 改版引发老用户不满，许多人偏好 v1 的极简界面。
  • 同步能力未明确定价与可靠性。

12my-tab 复刻实现建议#

12.1 建议的 MVP 范围

P0（先跑通闭环）：一键收起当前窗口 → 写入 chrome.storage.local → 打开列表页展示 → 单条/整组/全部恢复 → 导出/导入 → 选项页（固定标签、去重、恢复行为）→ 快捷键。

P1（体验补齐）：拖拽排序、多选、重命名、星标/锁定、文件夹、搜索栏 + omnibox、深色模式。

P2（差异化）：任务/备注、快捷列表、分享为网页、基于 OneDrive 的同步与备份（见 4.8.2）、回收站与防丢失。

12.2 架构建议

  • Manifest V3，后台用 Service Worker；所有状态落 chrome.storage，SW 只做编排。
  • 单写者模型：由 SW 串行处理所有写操作，页面只发消息；用 storage.onChanged 广播刷新。
  • 技术栈可选：原生 JS（最轻，OneTab 本身接近此路线）或 Vite + React/Preact（列表页交互复杂时更省力）。
  • 列表页与选项页复用同一套数据层（storage 适配器 + 纯函数 reducer），便于测试。

12.3 数据结构

沿用第 7.3 节草案。关键约定：

  • 每条 TabItem 用 uuid 作稳定 id，避免依赖浏览器 tabId（tabId 会话内有效且会复用）。
  • store.version 做 schema 版本化，为将来迁移留钩子——这正是 OneTab 的痛点，my-tab 应主动设计迁移器。
  • 大量标签时按组切键（如 group:<id>）以规避单值体积与写入放大。

12.4 关键技术点与坑

  • 先写库再关标签，且对「关闭失败/部分失败」做补偿。
  • 排除自身页面（列表页、选项页）不被收起。
  • 去重：按归一化 URL（去 fragment/常见 tracking 参数）判断。
  • favicon：优先用 favicon 权限或 Google t2.gstatic.com 服务；离线场景要降级为默认图标。
  • 无痕模式：需 incognito: "spanning" 或用户手动授权，注意隔离。
  • 大列表性能：列表页用虚拟滚动（OneTab 在数千条时变慢是已知短板，可作为超越点）。
  • 防丢失：内置导出快照 + 升级前自动备份 + 回收站（软删除）。
  • OneDrive 同步备份（见 4.8.2）：只读写一个 JSON 快照文件，同步交给 OneDrive 客户端；用目录句柄（File System Access API）实现静默自动备份，不可用时降级为 chrome.downloads 手动导出。合并按 id + updatedAt 做 LWW，删除用 deletedAt 软删除传递，避免复活。

12.5 建议的迭代路线

  1. M1：MV3 骨架 + 收起/恢复 + 本地存储 + 列表页（P0 闭环）。
  2. M2：组织能力（拖拽/文件夹/星标/锁定）+ 搜索 + 选项页完善。
  3. M3：防丢失（回收站/备份/迁移器）+ 大列表性能。
  4. M4：OneDrive 同步与备份（快照文件 + 合并策略）+ 分享为网页 + 跨浏览器适配。
